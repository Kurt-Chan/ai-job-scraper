# Systems

> Part of ai-job-scraper-clean/.project-knowledge/ | Last updated: 2026-08-16

| System | Status | Details |
|--------|--------|---------|
| AI / LLM | Working | Claude Code CLI invoked as a subprocess (`run_claude()` in `agent.py`), not the Anthropic API/SDK directly. Prompts live as files in `prompts/`, `--allowedTools Read` only (no Write — Claude prints, Python writes files). Seven call sites: resume analysis (`analyze_resume`), search-query building (`build_search_config`), job analysis/scoring, cover letter drafting, CV generation (`prompts/cv.md`), and the apply stage's drafter + reviewer (`prompts/apply_draft.md`, `apply_review.md`). The apply reviewer deliberately runs in **fresh context** with the draft passed inline, so it critiques the text rather than defending its own reasoning. `run_claude()` wraps subprocess `OSError` (e.g. a broken/stub `claude` binary) into a `RuntimeError` so failures surface as a readable message instead of a raw crash — see [[history]]. |
| Document generation | Working | Typst (`~/.local/bin/typst`) compiles Claude-generated `.typ` source into per-job CV PDFs (`_compile_cv`), then `pdftotext` (poppler) reads the text layer back to check what an ATS would see (`_verify_cv`): empty text, missing email, page overflow, and posting terms the resume supports but the CV omitted. Both binaries are optional at import time — a missing `typst` fails only that job, a missing `pdftotext` silently skips verification. |
| Search / Scrape | Working | Firecrawl (`firecrawl-py`) is primary: `app.search()` for discovery, `app.scrape()` with a JSON extraction schema for pulling individual postings off listing pages. Exa (`exa-py`, optional — `EXA_API_KEY`) is a fallback in `extract_postings()`/`_extract_via_exa()`: when Firecrawl's scrape fails or returns nothing (LinkedIn/Reddit reliably respond "Website Not Supported"), Exa's `get_contents()` with a schema-based `summary` option retries structured extraction on the same URL. Falls back further to the search snippet as a single posting if both fail. Discovery is decoupled from scraping: every candidate page found is persisted to `output/page_queue.json` and only `MAX_PAGES_TO_SCRAPE` (20) are scraped per batch, capped at `MAX_PAGES_PER_DOMAIN` (3) per site; "Find more jobs" works through the remainder without re-searching or re-scraping. |
| Background Jobs | Working | `server.py`'s `/api/run` spins the pipeline on a `threading.Thread`, guarded by a single `threading.Lock` so concurrent runs are rejected with a `busy` SSE event. `/api/apply` uses the same thread+queue pattern but is deliberately **not** lock-guarded — it's per-job and independent of a pipeline run. |
| Realtime | Working | Server-Sent Events (`StreamingResponse`) push pipeline step progress to the UI via a `queue.Queue` bridged into an async generator. |
| Auth | None | Local single-user tool, no auth anywhere. |
| Database | None | Flat JSON files under `output/` (gitignored) — see [[schema]]. |
| Storage | None | No file uploads. Cover letters, CV sources/PDFs, archived postings, and the `applications.csv` tracker are all written to `output/` by Python — see [[schema]]. |
